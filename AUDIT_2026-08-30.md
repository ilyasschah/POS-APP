**Scope:** `Back-End`, `Front-End`, `kitchen_display`, `octopus_dashboard_web`, `Octopus_Dashboard`, CI, repo hygiene

## Executive summary

This is a **strong codebase** — well above the norm for a single-developer
vertical product — with **one critical security regression** and **one
structural gap in CI** that together undercut much of the good work.

The engineering quality is genuinely high: tenant isolation is enforced globally
rather than remembered per call site, authorization is fail-closed, configuration
is validated at boot, and the inline commentary consistently explains *why* a
decision was made and what was tried before. There are **1,288 tests**, **zero**
`TODO`/`FIXME`/`HACK` markers, and **zero** stray `print()` calls across ~125k
lines of hand-written Dart and 734 C# files. That combination is rare.

Against that: **encryption-at-rest is currently switched off**, leaving customer,
order and payment data in a plaintext SQLite file on every terminal; and **CI
never runs the backend test suite and never validates a pull request**, so the
1,288 tests do not actually gate anything.

| 🔴 Critical | 1 | Encryption-at-rest disabled |
| 🟠 High | 4 | CI does not gate; repo bloat; Swagger + HTTPS in prod |

## 🔴 Critical

### C1. Encryption-at-rest is disabled — plaintext customer & payment data on every terminal

**`Front-End/lib/database/app_database.dart:6489`**

```dart
const bool kPillar3Encryption = false;
```

The SQLCipher-backed local database ("Pillar 3") is switched off. On launch,
`_decryptDbIfNeeded()` actively **decrypts any existing encrypted file back to
plaintext in place**. The resulting `pos_app.sqlite` sits in the OS documents
directory (`C:\Users\<user>\Documents\pos_app.sqlite`) and opens in any SQLite
tool with no key.

This is a *deliberate, documented* temporary state — `PROJECT_DOCUMENTATION.md`
§5 explains it was disabled to inspect offline-first writes in DBeaver/LINQPad,
and it carries a re-enable checklist that says **"Restore before shipping."**
The risk is not that it was done carelessly; the risk is that a flag like this
is exactly what ships by accident, and the offline-first work it was disabled
for is now largely complete.

Because the app is offline-first, this file is not a cache — it is the system of
record between syncs, holding orders, customers, and payment records. A stolen
or resold tablet, a backup, or any user with filesystem access reads all of it.

**Impact:** likely breaches PCI-DSS §3 (protection of stored cardholder data) and
GDPR Art. 32 (encryption of personal data) for any deployment handling either.

**Fix:** work the checklist already written in `PROJECT_DOCUMENTATION.md` §5 —
flip the flag, launch once so `_encryptLegacyDbIfNeeded()` re-encrypts in place,
delete plaintext copies exported for inspection, and confirm `PRAGMA
cipher_version` is non-empty at startup.

**Then make the regression impossible to repeat:** the flag is a compile-time
`const`, so a release build cannot detect it at runtime. Add a test asserting
`kPillar3Encryption == true`, or gate it on `kReleaseMode` so a release build
physically cannot open plaintext.

## 🟠 High

### H1. CI runs no backend tests and never validates a pull request

> **Status: addressed on this branch.** `.github/workflows/ci.yml` adds a
> `pull_request` trigger with four jobs — `dotnet test`, the POS app, the two
> companion Flutter packages, and the website. See the note under L2 for the
> broken scaffold test this surfaced.

There are **1,288 tests** (164 `[Fact]`/`[Theory]` methods in
`Back-End/Web-POS.Api.Tests`, 1,124 Dart tests across 105 files). Almost none of
them gate anything.

| Workflow | Trigger | Runs tests? |
|---|---|---|
| `deploy-backend-test.yml` | push to `test` | No |
| `deploy-dashboard-test.yml` | push to `test` | No |
| `release-macos.yml` | push tag | No — comment states it deliberately does not repeat `flutter analyze` / `flutter test` |
| `release-windows.yml` | push tag `v*` | `flutter test` only |

- **`dotnet test` appears nowhere in `.github/`.** The entire backend suite —
  including the tests that assert an unauthenticated `/admin` request redirects
  rather than 401s — has never run in CI.
- **No workflow has a `pull_request` trigger.** Nothing is checked before merge.
- The one `flutter test` runs at *release tag* time, which is the most expensive
  possible moment to discover a failure: the commit is already on `main`.
- `deploy-backend-test.yml` pushes straight to the OVH test box on every push to
  `test`, with no test run in front of the deploy.

**Fix:** add a `ci.yml` on `pull_request` + `push: [main, test]` running
`dotnet test` and `flutter analyze && flutter test` for all three Flutter
packages. This is the highest-leverage change in this document — the tests are
already written and paid for.

### H2. 1,417 build artifacts committed to git (41% of tracked files)

| Metric | Value |
|---|---|
| Tracked files total | 3,424 |
| Tracked build artifacts | **1,417** |
| Tracked `.dll` files | 1,415 |
| `.git` size | **293 MB** |

`.gitignore` *does* list `/build/`, `**/bin/`, `**/obj/` — and its comment shows
the intent was understood ("~300MB of artifacts… there is no reason for any of
it to be near the index"). But **`.gitignore` does not untrack files already in
the index**, so all of it is still versioned and still cloned by everyone.

Included in this is a directory literally named:

```
Back-End/Web-POS.Api/POS-APPbuildtest --nologoDebug/
```

— the fallout of a mis-quoted `dotnet build -o … --nologo` invocation, committed
and then replicated into four separate build trees.

**Verified clean:** every committed `appsettings.json` / `appsettings.Development.json`
under those build trees contains **placeholders only** — empty `DefaultConnection`,
`MasterConnection`, `Jwt:Secret`, `Lease:PrivateKeyPem`. **No `appsettings.Local.json`
is tracked anywhere.** The `.gitignore` comment warns these copies could carry local
credentials; on this commit they do not. The secret discipline held.

**Fix:** `git rm -r --cached` the build trees and commit. That stops the bleeding
in one commit and needs no history rewrite. Purging the 293 MB from history
(`git filter-repo`) is optional and separate — it rewrites every hash, so treat
it as its own coordinated change, not part of this.

### H3. Swagger UI is served unconditionally, including in production

**`Back-End/Web-POS.Api/Program.cs`**

```csharp
app.UseSwagger();
app.UseSwaggerUI(c => { … c.RoutePrefix = "swagger"; });
```

No `if (app.Environment.IsDevelopment())` guard. Every deployed environment
publishes a complete, browsable map of the API surface at `/swagger`.

The exposure is bounded — the global `FallbackPolicy` means the endpoints
themselves still demand a token, and `DocInclusionPredicate` limits the document
to controllers carrying `[SwaggerVisible]` — so this is reconnaissance value, not
direct access. It is still free reconnaissance.

**Fix:** wrap both calls in an environment check, or gate on a
`Swagger:Enabled` config flag defaulting to `false` outside Development.

### H4. HTTPS redirection is commented out

**`Back-End/Web-POS.Api/Program.cs`**

```csharp
//app.UseHttpsRedirection();
```

Combined with the admin portal's `CookieSecurePolicy.SameAsRequest` — chosen
deliberately, and correctly, because the portal is served over plain HTTP on the
LAN — an admin session cookie is transmitted in cleartext over the network. JWTs
from POS terminals travel the same way.

On a trusted store LAN this is a considered trade-off, and the code comments show
it was considered. For any internet-exposed deployment it is not survivable.

**Fix:** terminate TLS at IIS and enable redirection for the public deployment;
keep the LAN behaviour behind an explicit config switch rather than a commented
line, so the two deployment shapes are distinguishable at a glance.

## 🟡 Medium

### M1. ~150 FluentValidation validators run in observe-only mode — nothing is rejected

**`Back-End/Web-POS.Api/Behaviors/ValidationBehavior.cs:37`**

```csharp
// Defaults to FALSE — observe only. Set Validation__Enforce=true to enforce.
_enforce = config.GetValue<bool?>("Validation:Enforce") ?? false;
```

No `Validation` key exists in `appsettings.json` or `appsettings.Development.json`,
so the default applies everywhere: violations are **logged and then passed
through**. The ~150 `AbstractValidator` classes — previously never registered at
all, which the comment documents honestly — now execute but reject nothing.

This is a sound rollout strategy mid-flight, not a mistake. The risk is that
observe mode is invisible: everything looks wired up and validated, and it isn't.

**Fix:** review the accumulated observe-mode logs, fix over-strict rules, then set
`Validation__Enforce=true`. Give it a deadline — an observe mode with no end date
becomes permanent.

### M2. CORS falls back to `AllowAnyOrigin` when unconfigured

**`Back-End/Web-POS.Api/Program.cs`** — with no `Cors:AllowedOrigins` set (and
none is set in any committed `appsettings`), the policy is
`AllowAnyOrigin().AllowAnyHeader().AllowAnyMethod()`.

The code comment makes a fair point: the POS clients are native Windows/Android
apps not subject to CORS, and the admin portal is same-origin, so real exposure
is low. But this is a permissive-by-default that a future browser client silently
inherits — and the new marketing site plus `octopus_dashboard_web` are exactly
that. Note `AllowAnyOrigin` cannot be combined with credentials, which limits the
blast radius today.

**Fix:** set `Cors:AllowedOrigins` explicitly per environment; make the empty case
allow *nothing* rather than everything.

(Excluding generated code — `app_database.g.dart` at 60,956 lines and the ~36k

`sync_manager.dart` is the one that matters most: it is the offline-first

lines in a single file it is the hardest thing here to test in isolation or
review safely.

Flutter layer.

**Fix:** extract by feature rather than by layer, starting with `sync_manager.dart`
(pull/push/conflict-resolution/queue as separate units). Treat this as continuous
cleanup, not a project.

### M4. 67 hardcoded colors violate the project's own dark-mode rule

`CLAUDE.md` frontend rule #3 states: *NEVER use hardcoded colors like
`Colors.white`, `Colors.black`, or `Colors.grey[100]`.*

94 occurrences across 23 files. Splitting them honestly:

- **19 are defensible** — `Colors.black.withValues(alpha: …)` for shadows and
  scrims, which are conventionally black in both themes. `snackbar_helper.dart`
  correctly branches on `isDark`.
- **67 are real violations** — opaque fills and text colors that will invert
  wrongly in dark mode.

Worst offenders: `settings/settings_screen.dart` (24), `menu/menu_screen.dart`
(12), `bookings/bookings_screen.dart` (9), `core/app_theme.dart` (7).

**Fix:** replace opaque uses with `Theme.of(context).colorScheme.*`. Consider a
custom lint or a CI grep so the rule enforces itself — a written rule with 67
violations is not being enforced by anything today.

### M5. `.mcp.json` is Windows-only and carries machine-specific paths

```json
"command": "cmd",
"args": ["/c", "npx", "-y", "@executeautomation/database-server",
         "C:\\Users\\ILYASS\\OneDrive - Devaxy\\Documents\\pos_app.sqlite"]
```

Four of five servers invoke `cmd`, which does not exist on Linux or macOS — these
**failed to connect in this very session**. The config is committed, so every
non-Windows contributor inherits four broken servers. It also hardcodes a personal
`OneDrive` path and a LAN IP (`192.168.11.103:1433`).

Credentials are correctly parameterised (`${WEBPOS_DB_USER}`, `${GITHUB_PAT}`) —
that part is right.

**Fix:** drop the `cmd /c` wrapper (`npx` resolves cross-platform), and move the
SQLite path and DB host to environment variables.

The 197k-line `PROJECT_DOCUMENTATION.md` is otherwise an unusual asset — ADRs,

## What is genuinely good

Listing this because the findings above should not obscure it — and because
several of these are things most projects at this scale get wrong.

**Security architecture**
- **Fail-closed authorization.** `options.FallbackPolicy = RequireAuthenticatedUser()`
  means a newly added controller ships *protected*. The comment records that ~45
  controllers were once accidentally open — the fix was structural, not a sweep.
- **Tenant isolation as a global filter.** `CompanyScopeFilter` enforces
  `companyId` scoping for every action instead of relying on 251 correct call
  sites. The comment states the pre-fix behaviour plainly: any signed-in user
  could read another company's data by editing the URL. Fixing that with an
  opt-out filter (`[AllowCrossCompany]`) is the right shape.
- **`StartupConfigurationValidator`** aborts boot outside Development on a
  missing/short/placeholder JWT secret — a forged `Admin` token becomes
  impossible rather than merely unlikely.
- **Correct dual-scheme auth.** The admin portal's cookie scheme explicitly names
  itself via `AddAuthenticationSchemes`, with a comment explaining the redirect
  loop that results if it doesn't. That is a subtle bug, correctly pre-empted.
- **BCrypt for passwords, SQLCipher + HKDF device-bound keys, `flutter_secure_storage`.**
  The primitives are the right ones.

**Engineering discipline**
- **1,288 tests**, including integration tests that boot the real pipeline via
  `WebApplicationFactory<Program>` rather than a hand-rebuilt imitation.
- **Zero** `TODO`/`FIXME`/`HACK` markers and **zero** raw `print()` calls.
- **`flutter_lints` is enabled** — a prior audit in `PROJECT_DOCUMENTATION.md`
  flagged the ruleset as fully commented out; that regression has since been
  fixed.
- **No secrets in git.** Verified across every tracked `appsettings*.json`,
  including the stray build-tree copies.
- **Modern, deliberate dependencies** — Riverpod 3, Drift, MediatR 14, EF Core 10.

**Documentation**
The inline commentary is the standout. Comments explain *why*, record what was
tried and rejected, and flag traps — the `app_offline.htm` race in the deploy
workflow, the config-source ordering trap where `AddJsonFile` would let a local
file override a server env var, why an explicit Data Protection key folder was
removed after failing twice. This is institutional memory in the codebase, and it
is the main reason a project this size remains tractable for one developer.
