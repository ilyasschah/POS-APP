[B6] ITEM 42 - TWO TILLS, ONE DRAWER, NO INTERNET. BUILT.
     This is the one that lost money data, so read the
     "why" before the steps.

     WHAT WENT WRONG: two terminals share one register. A
     terminal only learns about the other one's session when
     it PULLS. Offline it never pulls, so its own database
     honestly says the drawer is free and it opens a second
     session. When the internet comes back the server takes
     the first push and refuses the second - "This register
     already has an open session" - and that row parked at
     sync_failed, which is TERMINAL. Every sale the second
     cashier rang was still on the tablet, pointing at a
     session the server would never own. Nothing retried it,
     nothing recovered it.

     TWO FIXES, because one was not enough:
     (a) A PRE-OPEN REFRESH. Press Open Register and the till
         now pulls the register's sessions FIRST. If one is
         already running you are told so and handed a
         "Sell in this session" button instead of opening a
         second. Bounded to 6 seconds and it fails OPEN - an
         offline till still opens its register exactly as
         before, because a shop with no internet must never
         be stopped from starting its day.
     (b) A MERGE when it happens anyway. The rejection is no
         longer a dead end. The till asks the server which
         session actually holds the register, moves its
         orders, documents, payments and cash in/out onto it,
         and deletes the duplicate.

     🚨 THE DETAIL THAT DECIDES THE DRAWER: the second till's
     OPENING FLOAT is deleted, not moved. The surviving
     session already carries its own counted float, and
     expected cash is opening + cash payments + cash in -
     cash out. Moving a second float across would put two
     floats on one drawer for money counted into it once.
     Watch for this in step (f).

     HOW TO TEST - you need two devices on ONE register:
     (a) Both devices: Settings -> Register, pick the SAME
         register. Confirm both show the same register name.
     (b) Device A, ONLINE: Open Register, float 200. Ring one
         sale. Let it sync.
     (c) Device B, ONLINE: press Open Register. You must get
         "This register is already open" and a single
         "Sell in this session" button - no float field. Tap
         it and ring a sale. Both sales must appear in the
         same session. 🚨 That is fix (a); before today B
         would have opened a second session here.
     (d) NOW THE REAL ONE. Close the session. Put BOTH
         devices in aeroplane mode / pull the network.
     (e) Device A: Open Register, float 200, ring 2 sales.
         Device B: Open Register, float 150, ring 3 sales,
         and do one Cash Out of 20. Both succeed - they are
         offline and neither can know about the other.
     (f) Put A back online, let it sync. Then B. Now on B:
         - No sync error, and nothing sits at "failed" in
           Sync Status.
         - POS Session shows ONE session, not two, with all
           FIVE sales in it.
         - Cash movements list shows ONE opening float of
           200 (A's), NOT two, and the 20 cash-out is there.
         - Expected cash at close = 200 + all cash payments
           - 20. If you see 350 of float, the merge moved
           something it should have dropped - tell me.
     (g) Close the register and check the Z-report covers all
         five sales once.

     ⚠️ WHAT IS DELIBERATELY NOT MERGED: a session device B
     had already CLOSED offline. Once a Z-report exists the
     payments carry its number, and moving them under another
     session would restate a slip already printed. That one
     still parks, and now says why. If you hit it, tell me -
     it needs a decision, not a silent repair.

     Covered by test/session_offline_conflict_test.dart
     (9 tests, including the float rule and the refusal to
     merge a closed session).

[B8] DATE FORMAT NOW ACTUALLY DOES SOMETHING.
     Settings -> General -> Regional -> Date Format had four
     options and changed NOTHING. Every screen and every PDF
     built its own 'dd/MM/yyyy' - about 85 places in the
     reports screen alone, plus thirteen other files.

     Now one setting drives all of them.

     🚨 FIXED AGAIN ON 2026-09-03 AFTER YOU CAUGHT THE FIRST
     PASS MISSING THE TABLES. You set yyyy-MM-dd, it saved,
     and Sales History still showed 01/09/2026 23:42. You
     were right, and you also spotted why: those columns
     carry a TIME as well as a date.

     WHAT I HAD MISSED: I swept for DateFormat('...') and
     fixed every one. But seven screens never called
     DateFormat AT ALL - they built the date by hand out of
     padLeft and string joins, WHILE ALSO converting the
     timezone:

         '${_pad(d.day)}/${_pad(d.month)}/${d.year} '
         '${_pad(d.hour)}:${_pad(d.minute)}'

     A search for DateFormat cannot see that. Those seven
     were: Sales History, Documents, POS Session, the Session
     list, the Document editor, Promotions, and the
     Subscription/About rows in Settings - plus the printed
     RECEIPT and the printed Z-REPORT slip, which had the
     same hand-rolled code. Every one of them is exactly the
     kind of screen that shows a date, which is why the miss
     was so visible.

     THE REAL LESSON, and why this is now one object: those
     screens had to do TWO things - apply the timezone AND
     format the date. Keeping the two apart is what let them
     drift. AppDateFormat now answers both, and a stored
     timestamp goes through one call. A bare calendar date is
     deliberately NOT timezone-shifted - shifting 2026-09-01
     by an offset is how a document dated the 1st starts
     displaying as the 31st.

     So when you re-test, the columns to stare at are the
     ones with a TIME in them: Date, Créé/Created, Opened,
     Closed. Those are the ones that were wrong.

     🚨 ONE DELIBERATE EXCEPTION, and I want you to agree
     with it: CSV EXPORTS AND FILE NAMES DO NOT FOLLOW THE
     SETTING. They are fixed at yyyy-MM-dd. A spreadsheet
     that reads your exports would otherwise change meaning
     the day somebody picks a different display format -
     silently, because 03/09 and 09/03 are both valid dates
     and neither one errors. File names also cannot contain
     "/" at all, and only sort chronologically as ISO.
     NOTE: today's CSV exports say dd/MM/yyyy, so this is a
     one-time change to their shape. Nothing is shipped yet
     (the API still points at your dev box, item 13), so now
     is the moment to make it. Say the word if you would
     rather they kept dd/MM/yyyy.

     HOW TO TEST:

     (b) 🚨 THE COLUMNS THAT WERE WRONG - do these FIRST,

         - POS Session: Opened at / Closed at, the payment

     (c) Then the rest: End of Day (Z-report history), Cash

     (d) Open the date-range picker anywhere. The selected
